# Контракт Запуска

Этот документ фиксирует текущий контракт запуска GUI после разгрузки первого старта.

## Основные Роли

`ApplicationController` создаёт главное окно, собирает `AppRuntime` и явно
подключает его к окну через `attach_app_runtime_to_window(...)`.

Главное окно создаётся напрямую в `ApplicationController`. Там же оно
регистрируется как активное окно приложения.

`window_runtime_setup.attach_app_runtime_to_window(...)` — единственное место,
где готовый `AppRuntime` подключается к окну. Сам файл остаётся коротким
координатором, а подробная сборка разнесена по маленьким setup-файлам:
lifecycle, уведомления, page deps и стартовые сигналы.

Порядок внутри этого шага важен:

```text
attach_window_lifecycle(...)
attach_window_notifications(...)
build_window_page_actions(...)
attach_startup_deps_to_window(...)
attach_window_ui_root(...)
restore_window_geometry(...)
connect_window_startup_signals(...)
start_window_deferred_init(...)
```

Окно на этом шаге не показывается. Его показывает `_deferred_init`
(`show_initial_window_if_needed`), когда интерфейс уже собран: см. правило 1 в
разделе «Одна работа за раз».

После этого `entry.py` не выполняет позднюю обвязку синхронно перед
`app.exec()`. Подключение Windows shutdown hook, оформление окна и IPC-сервер
ставятся через `QTimer.singleShot(0, ...)`, чтобы Qt event loop сначала начал
обрабатывать уже поставленную сборку UI.

Post-startup задачи не устанавливаются сразу в этом позднем bootstrap-шаге.
Они только подготавливаются и привязываются к `StartupInteractive`; реальная
установка идёт следующим Qt-событием после сигнала `startup_interactive_ready`.
Так импорты проверок, DNS, апдейтера и прогревов не попадают в стек сборки
первой страницы.

`WindowPageActions` создаётся после уведомлений, потому что действия страниц
используют `window_notification_center.notify`.

Feature-зависимости не собираются из полного окна. Для этого есть
`FeatureWindowDeps`: маленький явный набор Qt-parent, startup/close state и
callback-ов окна. Для страниц есть `WindowPageActions`, то есть отдельный набор
разрешённых действий окна. `WindowPageActions` не хранит полное окно: он
передаёт дальше только готовые callback-и.

`AppRuntime` — это тонкая сборка путей, состояния и feature-входов приложения.
Его создаёт управляющий слой приложения, а не само окно. `AppContext` в рабочем
потоке больше нет.

`WindowStartupMixin` отвечает за жизненный цикл окна во время старта:

- подготовить стартовое состояние окна;
- собрать основной UI, пока окна ещё нет на экране;
- показать окно сразу готовым;
- отметить `StartupInteractive`, когда основной UI уже собран и навигация готова;
- дать Qt короткий зазор на отрисовку и первый ввод пользователя;
- взять `WindowStartupRuntime`;
- создать `StartupCoordinator` через переданный callback;
- запустить `StartupCoordinator`;
- отметить метрики `StartupCoreReady`, `StartupPostInit`.

`ApplicationLifecycle` исполняет полный выход из приложения:

- скрыть tray-иконку;
- сохранить геометрию;
- остановить DPI, если пользователь выбрал выход с остановкой;
- очистить Premium, runtime threads, страницы и визуальные ресурсы;
- вызвать `QApplication.quit()`.

У выхода по одному владельцу на каждый шаг, и это закреплено проверкой
`check_process_exit_has_single_owners` в `app/architecture_checks.py`:

- программу закрывает только `ApplicationLifecycle` (`QApplication.quit()`).
  Остальной код просит выход через `request_exit`; код остановки winws после
  «остановить и выйти» вызывает переданное ему `on_stopped` и сам программу
  не закрывает;
- процесс завершает только `main/process_exit.py` (`finish_process`), а не
  обычный `sys.exit()`: он даёт потокам Qt и Python ограниченное время,
  выполняет шаги выхода и вызывает `os._exit` с кодом выхода;
- действие «при выходе» записывается только через
  `utils.exit_steps.register_exit_step`. Сейчас это закрытие журнала
  программы, журналов запусков winws и базы настроек, «Session ended» в
  журнале падений и освобождение мьютекса единственного экземпляра.

Объекты Qt при выходе не разрушаются: уборка PyQt при завершении
интерпретатора падала с нарушением доступа, когда обработчики программы
заводили новые объекты во время удаления окна (подробно — в описании
`main/process_exit.py`). Поэтому на деструкторы объектов Qt и на `atexit`
рассчитывать нельзя: всё, что должно сохраниться, делается либо в
`ApplicationLifecycle` до конца цикла событий, либо шагом выхода.

`ApplicationLifecycle` не хранит главное окно напрямую. Для действий, которым
всё ещё нужен Qt-объект окна, используется `ApplicationLifecycleWindowPort`.

`WindowLifecycleMixin` только принимает Qt-события окна и передаёт команды в
`ApplicationLifecycle`.

`StartupCoordinator` отвечает только за порядок запуска:

- подготовка runtime после `StartupInteractive`;
- основной стартовый контур после готовности UI;
- постановка post-init задач;
- постановка DPI autostart.

Startup-шаги внутри `StartupCoordinator` не выполняются плотным циклом в одном
проходе главного Qt-потока. Они ставятся по одному через очередь Qt с короткой
паузой между шагами. Так окно уже видно, навигация доступна, а цикл интерфейса
успевает обработать клики и перерисовку между подготовкой runtime, process
monitor и основным startup-контуром.

DPI autostart тоже не запускается в тот же момент, когда post-init только
поставлен. Он получает отдельную короткую задержку после post-init, чтобы
старт DPI не отнимал первый интерактивный момент у GUI.

`application_post_startup.py` собирает явные зависимости для поздних задач из
готового окна и готового `AppRuntime`. Самим post-startup задачам передаётся
`PostStartupHost`, а не полное окно.

`post_startup.py` только принимает `PostStartupDeps` и ставит поздние задачи.
Он не достаёт feature-ы из окна и не импортирует конкретные post-startup
модули на верхнем уровне файла. Конкретный установщик подгружается только при
реальном вызове.

`post_startup_*.py` отвечают за поздние задачи, но не все они ждут одного
сигнала:

- проверки, backend-прогревы Network/Premium/Appearance/Logs и прогрев профилей
  ставятся после `StartupInteractive` с короткими задержками, чтобы UI уже
  успел отрисоваться и принять первый ввод;
- DNS-применение, списки, Telegram Proxy, tray для обычного запуска,
  update-check и maintenance ставятся после `StartupPostInit`;
- часто открываемые страницы (профили, пресеты, Telegram Proxy, «Оформление»,
  Premium) могут собираться заранее, чтобы первый клик по ним не строил
  виджеты в GUI-потоке. Собрать виджет в фоновом потоке нельзя, а сборка в
  GUI-потоке — заминка окна на 50–120 мс, которую смотрящий на программу
  человек видит как рывок анимации. Поэтому это работа «про запас»
  (`speculative=True` в очереди `main/post_startup_idle_tasks.py`): по одной
  странице, только пока молчит фон (см. «Одна работа за раз») и только когда
  заминку некому заметить — человек работает в другой программе или давно не
  трогает мышь и клавиатуру. Пока он смотрит на окно, страницы не собираются
  вовсе и строятся по клику. По голому таймеру (`schedule_after`) страницы
  строить нельзя — это и давало рывки в первые секунды после запуска. Через
  ту же очередь, но как обычные задачи, идут окно «Что нового» и страница с
  окном обновления: они ждут только короткой паузы;
- данные для остальных страниц греются в фоне через backend-кэш.

## Одна Работа За Раз

В Python одновременно выполняется только один поток: остальные ждут общий
замок интерпретатора (GIL). GUI-поток отпускает его тысячи раз за сборку
одной страницы (каждый `addWidget`, каждое подключение сигнала, чтение файла
оформления) и каждый раз ждёт, пока фоновый поток вернёт замок. Поэтому
параллельная работа при запуске не ускоряет его, а растягивает. Замеры на
win10 при прежних настройках (интервал переключения замка 1 мс, у каждой
подсистемы свой поток):

```text
сборка страницы настройки профиля, фон молчит             72 мс
то же рядом с одним занятым фоновым потоком             2610 мс
то же рядом с тремя                                     9806 мс
16 пунктов меню + поиск, фон молчит                       ~5 мс
то же после показа окна, рядом с фоновыми задачами      ~500 мс
проверка каталога hosts сама по себе                      17 мс
она же при запуске рядом с шестью потоками             ~1100 мс
```

Цена одной передачи замка задаётся интервалом переключения
(`sys.setswitchinterval`, владелец — `ui/gui_thread_priority.py`). Пока окно на
экране, он равен 0,5 мс: Windows не умеет ждать меньше миллисекунды, поэтому
интервал в 1 мс длится ~2 мс, а интервал меньше 1 мс CPython округляет до
нуля. С ним та же страница рядом с одним занятым потоком собирается за 92 мс
(рядом с тремя — 160 мс). Поднимать интервал до 1 мс и выше нельзя. Точный
системный таймер Windows (`timeBeginPeriod`) программе не нужен: ожидание
замка от шага часов больше не зависит, а свои точные таймеры Qt ведёт сам.

Даже с коротким интервалом работа рядом идёт в полтора-четыре раза дольше,
чем по очереди, а фон на это время замедляется вдвое. Отсюда три правила
запуска.

1. **Всё видимое строится до первого показа.** Окно появляется на экране один
   раз и сразу готовым: `_deferred_init` сначала вызывает `build_ui` и только
   потом `show_initial_window_if_needed`. Показанное до сборки окно Windows
   выводит пустым и белым, и оно стоит так всё время сборки (180 мс на быстром
   компьютере, 260 мс и больше на обычном). Боковое меню целиком и поле
   поиска собирает `init_navigation` внутри `build_ui`, пока фоновых задач ещё
   нет. Достраивать видимую часть окна таймером после показа нельзя: окно
   перестраивается на глазах, а сама достройка попадает на одно время с
   фоновыми задачами и идёт в разы дольше. Пункты меню других режимов
   заранее не создаются — их добавляет `sync_nav_visibility` при смене режима.
   Заголовки групп меню встают на место сразу (`_settle_sidebar_header_animations`):
   библиотека растягивает их от нуля анимацией, и без этого пункты меню
   съезжали вниз уже на экране. Между `show()` и первой отрисовкой окно скрыто
   от экрана средством Windows (`ui/window_first_frame.py`), иначе оно на
   несколько десятков миллисекунд показывается пустым и белым.
2. **Фоновые задачи идут по одной.** `enqueue_subsystem_task` ставит задачу на
   общую дорожку `StartupLane` (`main/post_startup_threading.py`): задачи всех
   подсистем выполняются по очереди в порядке постановки. Свой поток есть
   только у очередей из `WAITING_QUEUES` — их задачи почти всё время ждут сеть
   или чужой процесс и замок не держат. `start_daemon_thread` — тоже только
   для задачи, которая ждёт. Задача с `warmup=True` (готовит кэш страницы
   заранее) пропускает вперёд всё, что нужно программе для работы, а задача с
   `on_screen=True` (её результат сразу виден на открытой странице, как
   плитка «Профили» на главной) идёт раньше остальных.
3. **GUI-поток и дорожка работают по очереди.** Очередь скрытых страниц не
   начинает сборку, пока дорожка занята или обход запускается, а дорожка не
   начинает следующую задачу, пока страница собирается (`gui_build_turn`).

Новая фоновая задача запуска, занятая диском или процессором, идёт только
через `enqueue_subsystem_task`. Отдельный `threading.Thread` для неё возвращает
ту же борьбу за замок.

## Что Не Создаётся На Первом Старте

На первом старте не создаются:

- `HostsManager`;
- `DNSUIManager`;
- `DiscordManager`;
- старый `UIManager`.

`HostsManager` создаётся при открытии hosts-страницы. DNS при старте идёт через DNS startup worker. `DiscordManager` создаётся лениво только при реальной попытке перезапуска Discord.

## Канонические Startup-Метрики

- `StartupTTFF` — первый показ окна.
- `StartupInteractive` — окно уже готово к первому взаимодействию.
- `StartupCoreReady` — основной стартовый контур готов.
- `StartupPostInit` — post-init задачи поставлены.
- `StartupDpiAutostart` — DPI autostart передан в поздний запуск.

При запуске скрыто в трее окно специально не показывается сразу. В этом режиме
`StartupInteractive` означает, что UI уже собран и готов к последующему показу,
а `StartupTTFF` может появиться сильно позже — в момент первого открытия окна
из трея или через IPC.

Все startup-метрики должны начинаться с `Startup...`.
Метрики задач, которые действительно ждут `StartupPostInit`, должны начинаться
с `StartupPostInit...`. Метрики вида `StartupPage...WarmupQueued` запрещены:
это след старого прогрева страниц по таймеру, которого больше нет.

Чтобы увидеть, чем GUI-поток занят в первые секунды, программу запускают с
переменной окружения `ZAPRET_UI_JITTER_MS=30`: в лог попадает каждая задержка
кадра дольше 30 мс со стеком GUI-потока и списком занятых фоновых потоков.

## Fluent UI

Production-интерфейс требует `qfluentwidgets`. Если этой библиотеки нет, это
ошибка окружения запуска, а не повод строить запасной интерфейс на обычных
Qt-кнопках и полях.
